# OrderKiosk 사용자 성장 · 수익화 설계

- 날짜: 2026-07-07
- 상태: 사용자 승인 완료 (브레인스토밍 세션)
- 관련 문서: [스토어 문안 + 스크린샷 구성안](../../store-listing-aso.md)

## 배경과 목표

OrderKiosk는 음성 주문 햄버거 키오스크 시뮬레이션 앱으로, 현재 수익은 AdMob 배너(주문 화면 하단) + 전면 광고(주문 2회당 1회)뿐이다. 수익을 키우는 전략으로 **인앱 결제나 광고 밀도 확대가 아니라, 사용자 수를 먼저 늘려 광고 수익 기반 자체를 키우는 방향**을 택했다.

성장의 축은 **"어르신 키오스크 연습 앱" 리포지셔닝**이다. 한국에서 키오스크 사용이 어려운 디지털 취약계층 수요가 크고 검색량이 있는 니치("키오스크 연습", "키오스크 사용법")이며, 경쟁 앱이 적고 복지관·언론 등 오가닉 유입 경로도 열려 있다. 현재 앱(한국어 음성 주문 시뮬레이션)이 이미 이 용도에 거의 부합한다.

### 검토 후 기각한 대안

- **키즈 역할놀이 포지셔닝**: 타겟을 어린이로 선언하면 Google Play 가족 정책이 적용되어 광고 SDK 인증·전면 광고 제한 등 광고 수익화가 크게 제약된다. 광고 수익 목표와 정면 충돌하므로 기각. (아이들이 앱을 쓰는 것 자체는 막지 않는다 — 스토어 문구에서 어린이를 타겟으로 선언하지 않을 뿐이다.)
- **이중(온 가족) 포지셔닝**: ASO는 검색어 집중이 생명인데 넓게 잡으면 어떤 키워드에서도 상위 노출이 어렵다. 기각.

## 1단계 — ASO + 측정 기반 만들기

코드 변경을 최소화하면서 검색 유입을 뚫고, 효과를 측정할 수단을 마련한다.

### 1-1. 스토어 리스팅 개편 (코드 작업 없음)

- 제목을 "키오스크 주문 연습" 계열로 변경, 짧은/전체 설명을 연습·부모님·음성 주문 키워드 중심으로 재작성, 스크린샷을 주문 흐름 순서 + 캡션으로 재구성.
- "연습용 앱, 실제 결제 없음"을 리스팅에 명시해 어르신 사용자의 불안을 제거.
- 구체 문안(한/영)과 스크린샷 구성안은 [store-listing-aso.md](../../store-listing-aso.md) 참조. 등록은 사용자가 Play Console에서 직접 수행.

### 1-2. Firebase Analytics 재활성화 (소규모 코드 작업)

Firebase BOM + Analytics 의존성과 `google-services` 플러그인이 이미 Gradle에 남아 있으므로, 이벤트 로깅 코드만 추가한다. 최소 이벤트 세트:

| 이벤트 | 파라미터 | 목적 |
|---|---|---|
| `order_started` | `locale` (ko/en) | 주문 시작 수, 언어 비율 |
| `order_completed` | `locale`, `item_count` | 주문 완료율 → 어르신이 끝까지 진행하는지 |
| `voice_input_used` | — | 음성 vs 터치 주문 비율 |

- 이벤트 로깅 지점: `OrderFragment`(주문 시작), `OrderCompleteFragment`(완료), `MainActivity`(음성 인식 결과 수신 시).
- CLAUDE.md의 "Firebase 사용 추가 금지" 문구는 잔재 정리 취지의 메모였으므로, Analytics 재활성화에 맞춰 해당 문구를 갱신한다.

### 1-3. 광고 현상 유지

배너 + 주문 2회당 전면 광고 구조는 1단계에서 변경하지 않는다. 사용자가 늘어난 뒤 데이터를 보고 조정한다.

### 1단계 성공 기준

- 리스팅 개편 후 4주간 Play Console 검색 노출 수·설치 수가 개편 전 대비 유의미하게 증가.
- Analytics로 주문 완료율 기준선(baseline) 확보.

## 2단계 — 콘텐츠 확장 (1단계 데이터 확인 후 착수)

포지셔닝을 실제 기능으로 뒷받침해 리텐션과 입소문을 만든다.

### 2-1. 어르신 모드 (우선순위 1)

설정 또는 첫 화면의 토글 하나로 켜는 모드:

- **큰 글씨**: 메뉴·버튼 텍스트 크기 확대. 테마/스타일 레벨에서 처리.
- **천천히 말하기**: TTS `setSpeechRate`를 낮춰 안내 음성 속도 감소. TTS는 `MainActivity`가 소유하므로 변경 지점이 한 곳.
- 상태는 별도 SharedPreferences 파일에 저장 (기존 `ad_preferences` 패턴과 동일).
- Analytics 이벤트로 사용률 측정.

### 2-2. 카페 시나리오 (우선순위 2)

한국에서 가장 흔한 키오스크인 카페를 첫 신규 콘텐츠로 추가한다. 기존 햄버거 흐름을 그대로 재사용한다:

- **데이터**: `res/raw/menu_data_cafe.json` / `menu_data_cafe_en.json` 추가. 기존 `Food.Type` 4분류를 커피/논커피/디저트에 매핑 — 데이터 모델 변경 없이 JSON 추가만으로 처리하는 것이 목표.
- **옵션**: HOT/ICE·사이즈는 기존 옵션 맵(String→가격) 구조로 표현.
- **진입**: 앱 시작 시 "햄버거 가게 / 카페" 선택 화면을 `OrderFragment` 진입 전에 추가. 큰 버튼 2개의 가벼운 화면으로 유지하고 기본값은 햄버거.
- **핵심 검증 포인트**: 세트메뉴 로직(`menu_combo`)이 없는 카페 메뉴에서도 `OrderChildrenBaseFragment.next()` 흐름이 자연스럽게 진행되는지.

### 2-3. 백로그 (이번 설계 범위 밖)

편의점·영화관 시나리오, 연습 완료 칭찬/수료증 화면. 카페 시나리오의 반응을 보고 결정.

### 2단계 성공 기준

- 어르신 모드 사용률, 카페 시나리오 선택 비율 (Analytics).
- D7 리텐션 개선 여부 (Play Console).

### 리스크

- 시나리오 선택 화면 추가로 기존 사용자의 진입 단계가 하나 늘어난다. 기본값 햄버거 + 가벼운 화면으로 마찰을 최소화한다.
- 카페 메뉴가 세트메뉴 로직을 우회하는 경로는 기존 코드에서 충분히 검증되지 않았을 수 있다. 2단계 구현 계획에 흐름 테스트를 포함한다.

## 범위 외

- 인앱 결제/구독, 광고 형식 변경(네이티브·리워드·앱 오픈 광고), B2B 라이선스 모델.
- 이들은 사용자 규모가 확보된 뒤 별도 설계로 다룬다.
